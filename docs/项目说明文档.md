# WanderInk（漫游墨绘）项目说明文档
> 适用赛事：第二届 NVIDIA DGX Spark 黑客松

---

## 一、项目概述

**WanderInk（中文名“漫游墨绘”）** 是一款面向景区文化 IP 开发的端到端多模态创作系统。用户只需输入一个景区名称，系统即可自动完成传说检索、剧本改编、分镜设计、角色设定、连环画绘制、配音配乐与视频合成，最终输出一部可播放、可分享的**1080P 有声连环画短视频**。

核心 slogan：

> **景区名称进，有声连环画出。**

本项目在第一届 Spark 黑客松项目 [SparkScroll](https://github.com/zhanghui-china/SparkScroll) 的产品理念基础上进行了全面升级：从“纯漫画”升级为“有声有画的多媒体叙事”，从“大模型直接生成剧本”升级为“引入电影业界编剧/导演 skill 的专业化创作”，从“全自动黑盒”升级为“分步可干预、可重跑、可审校的创作工作台”，从“后台网关为主”升级为“支持多用户协作、界面友好的完整 Web 应用”。本届团队除队长外引入了更多具备影视、AI 工程、前后端全栈经验的专业人才。

## 二、作品特点与核心亮点

### 2.1 端到端全链路自动化

系统把景区故事创作拆分为 **S0–S6 七个顺序步骤**，覆盖文本、图像、语音、音乐、视频五种模态，单条流水线即可从“景区名”直达“MP4 成片”，无需人工切换工具：

| 步骤 | 名称 | 产出物 |
|---|---|---|
| S0 | LEGEND 传说检索与甄别 | 2–5 条候选传说及来源标注 |
| S1 | SCRIPT 剧本改编 | 结构化剧本（幕/场/对白/旁白） |
| S2 | BOARD 分镜设计 | 分页分镜表（画面描述/情绪/文案） |
| S3 | ROLE 角色设定 | 角色卡 + 正/侧/背三视图 |
| S4 | PAGES 连环画页生成 | 逐页 1920×1080 画面 |
| S5 | VOICE 配音配乐 | 逐页解说音频 + BGM |
| S6 | FILM 合成输出 | 带字幕/水印/片尾的 MP4 |

### 2.2 角色一致性无需训练

项目最大技术亮点是 **“三视图 + 参考图注入”** 的角色一致性方案：

- S3 为每个主要角色生成正/侧/背三视图；
- S4 将三视图缩放到 768px 后作为图像参考图传入生成请求；
- 配合固定画风前缀与角色特征 prompt，约束跨页形象。

在 M0 一致性门禁中，白蛇传 2 角色 × 3 画风 × 24 张图的抽样评估达到 **100% 零身份漂移**，标志道具（银簪、纸伞等）全程保留，验证了“不微调 LoRA 也能保持高一致性”的工程路径。

### 2.3 音画同步与健壮音频

- S5 按真实音频时长写回 `duration_ms`，S6 据此精确计算每页长度与转场 offset；
- TTS 采用“整段单发优先 + 截断检测退化到分句 + 三试取最长”的策略，兼容强模型与弱模型；
- 当 TTS 完全不可用时，系统按字数估算时长生成静音兜底轨，保证成片结构完整、不残缺。

### 2.4 分步可干预的创作工作台

与完全自动的“一键到底”不同，WanderInk 默认支持分步确认：

- 每步产物均在前端可视化预览；
- 用户可修改剧本、调整分镜、重绘单页、重配单音、拖拽排序；
- 任意步骤崩溃后，基于 `project.json` 的断点续跑机制只补缺失部分，不重做已完成工作。

### 2.5 专业化 Skill 驱动

项目引入 **Hermes Agent**（底层配置 glm5.2 模型）承载“编剧大师”与“导演大师”两个专业 skill，覆盖 S1–S3 全部文本生成环节：

- **编剧大师 skill**：负责 S1 剧本改编，输出更符合影视叙事结构（冷开场、起承转合、主角 ≤3）的剧本；
- **导演大师 skill**：负责 S2 分镜拆分与 S3 角色特征提取，输出带镜头语言（全景/中景/特写、光线、氛围）与情绪标签的分镜表。

Hermes 的接入为流水线注入了电影行业知识，使生成内容从“通用 LLM 出文本”升级为“受专业创作方法论约束的结构化产出”。WanderInk 只需通过 OpenAI 兼容协议以 `hermes-agent` 作为模型名调用该服务，底层模型与 skill prompt 的组合由 Hermes 内部托管。

## 三、技术实现方案

### 3.1 整体架构

项目采用 **“Supervisor + 顺序流水线 + 可插拔 Provider”** 架构：

- **单一 `Project` 聚合根**：所有中间态（候选传说、剧本、分镜、角色卡、页面产物、输出）都挂在同一个 Pydantic `Project` 对象上，序列化为 `projects/<id>/project.json`，是唯一事实源；
- **OpenAI 兼容 Provider 层**：LLM / Image / TTS / Music 四个 provider 全部走 OpenAI 兼容协议，通过 `.env` 或 Web 配置面板切换端点、模型、密钥，业务代码零改动；
- **CLI / HTTP 双入口**：`shanhai`（Typer CLI）与 `shanhai-web`（FastAPI）复用同一套 `steps/*` 与 provider 层，HTTP 端将管线丢入后台线程，前端轮询进度；
- **FFmpeg 函数式合成**：`ffmpeg.py` 纯命令构造，S6 按“片头卡 → 逐页 → 片尾卡 → xfade 拼接 → 响度归一化 + BGM”串联落地。

### 3.2 多 Agent 角色设计

| Agent | 职责 | 底层能力 |
|---|---|---|
| StoryAgent | 景区 → 历史故事概要（S0） | 大纲生成 |
| ScriptAgent | 故事 → 剧本（S1） | Hermes 编剧大师 skill |
| DirectorAgent | 剧本 → 分镜（S2） | Hermes 导演大师 skill |
| CharacterAgent | 剧本 → 人物小传与道具描述（S3） | 图像编辑 |
| ImageAgent | 角色三视图、分镜漫画（S3/S4） | 图像编辑 |
| VoiceAgent | 分镜文本 → 解说语音（S5） | 语音合成 |
| MusicAgent | 情绪标签 → 背景音乐（S5） | 音乐生成 |
| ComposerAgent | 画面 + 语音 + 音乐 → MP4（S6） | FFmpeg + PIL 排版 |

### 3.3 关键技术细节

- **字幕与画面分层**：`compose_page()` 只出 1920×1080 满幅底图，`overlay_layer()` 单独生成透明 PNG 承载字幕与“AI 生成”水印；ffmpeg 中 overlay 在 Ken Burns 缩放之后叠加，避免文字随镜头抖动或水印被裁出画面。
- **原子写与可重入**：`store.save()` 采用“写 `.tmp` 后 `os.replace`”的原子写，每步落盘；S3 `locked` 幂等、S4/S5 产物存在性校验，支持任意步骤崩溃后断点续跑。
- **本地后端全局单并发**：`providers/_http.py` 通过 `local_backend_guard` 自动识别 `127.0.0.1`/`localhost` 端点，对 DGX Spark 上共享 GPU 的 Ollama/vllm/ComfyUI/Qwen-TTS/ACE-Step 进行全局排队，避免多任务抢卡导致超时。
- **按环节配置覆盖**：Web 配置面板支持“全局默认 + S0–S5 按环节覆盖”，例如 S1–S2 全部走 Hermes 编剧/导演 skill（底层 glm5.2），图像走云端或本地 ComfyUI，无需重启即可生效。

## 四、架构设计思路与优化方案

### 4.1 DGX Spark 平台适配思路

DGX Spark（GB10，128GB 统一内存）的核心约束是“多模型无法同时驻留”。因此本项目没有试图把所有模型同时加载，而是采用 **分时加载 + 本地服务 shim + 全局单并发锁** 的策略：

1. **文本阶段**：VLLM 本地 LLM（`Sehyo-Qwen3.5-35B-A3B-NVFP4`）常驻约 35GB；
2. **图像阶段**：通过 `shanhai-image.service` 桥接到 ComfyUI（`Qwen-Image-Edit-2511`）；
3. **音频阶段**：`shanhai-tts.service`（`Qwen3-TTS`）与 `shanhai-music.service`（`ACE-STEP 1.5 XL`）分时复用 GPU；
4. **合成阶段**：ComposerAgent 仅消耗约 2GB，使用 ffmpeg 完成最终输出。

这种设计充分发挥了 DGX Spark **大统一内存、单机多模态协同、本地闭环推理** 的平台优势。

### 4.2 已落地的关键优化

| 优化项 | 问题 | 方案 | 效果 |
|---|---|---|---|
| 角色一致性 | 跨页人物形象漂移 | 三视图参考图 + 768px 缩图上传 + 固定画风前缀 | M0 门禁 100% 通过 |
| 竖图填充 | gpt-image-2 出竖图导致黑边 | 完整画面居中 + 同图模糊压暗填充两侧 | 成片观感专业 |
| S4 并发 | 逐页串行太慢 | ThreadPool 上限 3，本地 GPU 自动串行 | 云端场景提速约 23% |
| 静音兜底 | TTS 不可用导致成片残缺 | 字数估算时长生成静音轨 | 端到端即使 TTS 全失败也能出片 |
| 网络容错 | 代理瞬时 503/RemoteProtocolError | 捕获完整 `httpx.TransportError` 家族并指数退避 | 真实 DGX 部署稳定性提升 |
| 配置面板 | 改端点需改文件重启 | Web UI 运行时覆盖，持久化到 `config.json` | 无需重启即可切换模型 |
| GPU TTS | DGX 无在线 TTS | 部署 Qwen-TTS shim，PyTorch nightly 适配 GB10 sm_121 | 本地真人声已跑通 |
| AI BGM | 曲库为空 | ACE-STEP 1.5 XL 本地生成纯器乐 BGM | S5 已可输出真实配乐 |

### 4.3 优化方案

以下功能已实现：

- **多用户登录与队列可见性**：Cookie session + `users.json`，支持团队共用、只看自己的取消权限；
- **全国5A级景区信息录入**：从文旅局官网抽取359家5A级景区信息，允许用户快捷输入

以下功能规划中：

- **单页多格漫画排版**：支持日式多格分镜，提升镜头节奏与画面层次；
- **角色库跨项目复用**：将锁定角色存入全局库，减少重复生成；
- **PDF 精排版与多语言输出**：面向 B 端景区运营方；
- **成本上限与重绘预算控制**：防止远程 API 额度失控；
- **支持自定义三视图**：允许用户自行设计IP形象
- **支持真实景区图片合成**：允许用户上传真实景区图片合成漫画和视频

## 五、AI 合规性处理与敏感信息管理

本项目将 AI 内容合规作为**不可关闭的硬规则**内建到合成流程：

1. **每页“AI 生成”水印**：透明 overlay 层右上角恒定显示描边水印，不随 Ken Burns 镜头运动失效；
2. **AI生成标识**：图片和视频均明确标注“WanderInk AI辅助生成”字样；
3. **来源精确标注**：按 `source_type` 区分“正史 / 地方志 / 民间传说 / 文学作品 / 原创演绎”，原创演绎不冒充传说来源；
4. **敏感内容过滤**：S0 对涉及宗教、民族、近现代政治人物的候选传说进入敏感审校清单；用户手册明确提示此类景区可走“自备故事”路径；
5. **儿童向内容保护**：儿童受众自动规避暴力/恐怖细节；
6. **版权边界**：用户上传自备故事需自行承诺权利；系统输出物明确标注来源与 AI 生成身份。

未来规划：引入输入/输出双侧内容安全过滤 API，对文生图 prompt 与生成结果进行自动审核。

## 六、部署方案 

### 6.1 安装ComfyUI环境

```bash
#使用wuzi用户登录
source ~/.bashrc

#安装依赖
sudo apt-get install -y sox libsox-fmt-all

#创建conda环境
conda create -n comfyui python=3.12 -y
conda activate comfyui

#下载ComfyUI代码仓
cd ~
git clone https://github.com/comfyanonymous/ComfyUI.git

#根据显卡 CUDA 版本安装对应的 PyTorch
pip3 install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu130

#安装ComfyUI依赖
cd ~/ComfyUI
pip install -r requirements.txt
```

编辑\~/.config/systemd/user/comfyui.service文件，配置systemctl常驻服务

```
[Unit]
Description=ComfyUI User Service
After=network.target

[Service]
Type=simple
WorkingDirectory=/home1/wuzi/ComfyUI
Environment="HF_ENDPOINT=https://hf-mirror.com"
ExecStart=/home1/wuzi/anaconda3/bin/conda run --no-capture-output -n comfyui python main.py --listen 0.0.0.0 --port 8188 --use-flash-attention --gpu-only
Restart=always
RestartSec=10
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=default.target
```

### 7.1 Nvidia和阶跃星辰模型

#### 7.1.1 Sehyo-Qwen3.5-35B-A3B-NVFP4模型

本项目选用 **Sehyo/Qwen3.5-35B-A3B-NVFP4** 作为 DGX Spark **本地部署**的核心文本模型之一。该模型基于 Qwen3.5-35B-A3B MoE 架构量化而来，在保持原模型能力的同时，完整保留了 **MTP（Multi-Token Prediction）** 权重，可进一步结合 vLLM 的 **Speculative Decoding（投机解码）** 技术提升推理吞吐，是当前 Qwen3.5 系列中兼顾性能、成本与部署效率的高性价比方案。

该模型采用 NVIDIA Blackwell 平台原生支持的 **NVFP4（NVIDIA Floating Point 4-bit）** 量化格式。NVFP4 通过 **FP4 权重 + FP8 Scale** 的混合设计，在极大降低模型存储与计算开销的同时，尽可能保持模型精度。相比原始 BF16 模型，NVFP4 可实现约 **4 倍模型压缩率**，显著降低显存占用和显存带宽压力，从而提升 GPU 数据读取效率。

与传统 INT4 量化方案相比，NVFP4 采用浮点表示方式，对不同数值范围的权重具有更好的表达能力，能够有效减少量化误差，保持模型推理精度。对于 Qwen3.5-35B-A3B 这类 MoE（Mixture of Experts）模型而言，NVFP4 能够更好地保留各 Expert 的能力特征，降低量化后性能衰减风险。

依托 NVIDIA Blackwell 架构对 NVFP4 的原生支持，模型推理过程可直接利用 Tensor Core 进行硬件加速，在保证生成质量的前提下，实现更高的 Token 生成速度和 Batch 吞吐能力。对于本项目的大模型 Agent、多轮对话、代码生成、数据分析等场景，能够在有限算力资源下获得更优的部署效果和运行效率。

**综合来看，Sehyo/Qwen3.5-35B-A3B-NVFP4 在模型能力、推理性能、显存占用以及部署成本之间取得了良好的平衡，是 DGX Spark 本地化大模型推理平台的重要基础模型之一。**

在本项目中，ACE-Step 1.5 XL 主要承担场景背景音乐生成以及音频素材快速制作等任务。通过自然语言驱动的音乐生成方式，项目能够在无需专业音乐制作团队参与的情况下，快速获得符合剧情和场景需求的原创音乐内容，大幅降低内容生产门槛，提高创作效率。模型支持较长时长音乐内容生成，可满足短剧、连环画视频、宣传片以及数字内容创作等多种场景需求。

作为阶跃星辰生态的重要生成式 AI 能力之一，ACE-Step 1.5 XL 为本项目补齐了从文本生成、图像生成到音乐生成的完整 AIGC 内容生产链路。通过与大语言模型、多 Agent 系统以及视觉生成模型的协同工作，实现了“故事生成—角色塑造—画面创作—音乐制作”的全流程智能化内容生产闭环。

**综合来看，ACE-Step 1.5 XL 在音乐质量、生成效率以及创作自由度之间实现了良好的平衡，为本项目提供了专业级 AI 音乐创作能力，是构建多模态内容生成系统的重要组成部分。**

### 7.2 常用工具和Nvidia SDK

#### 7.2.1 vLLM：文本大模型推理服务框架选型

在本项目中，我们将大模型推理能力视为整个系统的核心基础设施，而不仅仅是简单的模型调用。因此，在推理框架选型阶段，我们重点考察了推理性能、GPU利用率、长上下文支持、多模型兼容性以及后续扩展能力等多个维度，最终选择 **vLLM** 作为统一的大模型推理引擎，并采用 **Docker 容器化部署** 的方式构建模型服务层。

目前开源生态中常见的大模型部署方案主要包括 **Ollama、llama.cpp、SGLang 和 vLLM**。其中，Ollama 更适合个人开发者快速体验和本地部署模型，具有安装简单、使用门槛低等优势，但其定位更偏向于模型运行时（Model Runtime），在高并发推理、GPU资源调度以及生产级服务化部署方面能力相对有限。llama.cpp 则以极致的轻量化和跨平台能力著称，尤其适合 CPU、Mac 以及边缘设备部署场景，但其主要围绕 GGUF 量化生态构建，对于高端 GPU、超大规模模型以及新一代量化格式的支持能力相对有限。

SGLang 与 vLLM 则代表了当前开源社区中面向生产环境的大模型推理框架发展方向。SGLang 在 Structured Generation、Function Calling 和 Agent 工作流场景中具有较强优势，而 vLLM 则凭借成熟的工程生态、更广泛的行业应用验证以及对 NVIDIA GPU 生态的深度适配，成为目前企业级私有化部署和 AI Agent 平台中应用最广泛的推理引擎之一。

综合项目需求与硬件环境考虑，本项目最终选择 vLLM 作为统一推理服务框架。首先，vLLM 提供与 OpenAI API 完全兼容的接口规范，能够方便地接入 Gateway、Agent Orchestrator 以及业务应用层，实现模型能力的统一封装与管理。其次，vLLM 的核心技术 **PagedAttention** 能够显著提高 KV Cache 利用率，有效减少显存碎片和内存浪费，在长上下文和多用户并发场景下充分释放 GPU 算力资源。同时，vLLM 支持 **Continuous Batching（连续批处理）**，能够动态合并不同用户的推理请求，提高 GPU 利用率和整体系统吞吐能力。

本项目采用的核心文本模型 **Sehyo/Qwen3.5-35B-A3B-NVFP4** 保留了 **MTP（Multi-Token Prediction）** 权重，而 vLLM 已具备对 **Speculative Decoding（投机解码）** 等先进推理优化技术的支持能力，可以进一步提升 Token 生成速度和推理吞吐量。此外，vLLM 对 NVIDIA Blackwell 架构以及 FP8、FP4 等新一代量化技术具备良好的兼容性，能够充分发挥 DGX Spark 平台的硬件性能优势。

在部署方式上，本项目采用了官方提供的 **vLLM Docker 镜像** 进行容器化部署，而非直接通过 Python 环境安装运行。这样做的主要原因在于，大模型推理环境涉及 CUDA、PyTorch、NCCL、FlashAttention、Transformer Engine 等大量底层依赖，不同版本之间往往存在复杂的兼容关系。通过 Docker 镜像可以将整个推理环境进行标准化封装，确保开发环境、测试环境和运行环境保持一致，显著降低部署和运维复杂度。

同时，DGX Spark 所搭载的 NVIDIA Blackwell GPU 平台对 CUDA Runtime、驱动版本以及 NVFP4 等新特性具有较高要求，官方镜像已经完成了相关依赖组件的适配和优化工作，能够减少环境配置风险，提高系统稳定性。容器化部署方式也为后续迁移至其他 NVIDIA GPU 平台、云端 GPU 集群或 Kubernetes 环境提供了良好的兼容性和可扩展性。

综上所述，本项目采用 **vLLM + Docker** 的技术方案，不仅能够充分发挥 DGX Spark 和 Blackwell GPU 的硬件性能优势，还能够通过 PagedAttention、Continuous Batching、Speculative Decoding 等核心技术实现高吞吐、低延迟、长上下文的大模型推理服务。同时，该方案具备良好的工程化能力、可维护性和扩展性，为未来多模型协同、多 Agent 工作流以及大规模并发访问场景提供了坚实的基础设施支撑。

#### 7.2.2 CUDA 13.0：GPU计算平台与 CUDA 技术

为了充分发挥 NVIDIA DGX Spark 平台的硬件性能，本项目采用 **CUDA 13.0** 作为底层 GPU 计算运行环境，为大模型推理、多模态内容生成以及 AI Agent 工作流提供统一的高性能计算基础设施支持。

CUDA（Compute Unified Device Architecture）是 NVIDIA 推出的通用并行计算平台和编程模型，也是当前人工智能领域事实上的标准 GPU 计算生态。现代大模型训练与推理框架，包括 PyTorch、TensorRT、vLLM、FlashAttention、Transformer Engine 等核心组件，均构建在 CUDA 生态之上。CUDA 不仅负责管理 GPU 资源调度和计算任务执行，还提供了高性能数学库、通信库以及针对 AI 场景优化的 Tensor Core 加速能力，是整个 AI 技术栈的基础运行平台。

相较于早期 CUDA 版本，CUDA 13.0 针对 NVIDIA 新一代 **Blackwell 架构 GPU** 进行了深度优化，能够更好地支持大模型推理场景中的高吞吐计算需求。特别是在 FP8、FP4 等低精度计算格式支持方面，CUDA 13.0 提供了完整的软件栈支持，使得新一代量化模型能够充分利用 Blackwell Tensor Core 的计算能力，在保证模型精度的同时显著提升推理效率。

本项目采用的核心文本模型 **Sehyo/Qwen3.5-35B-A3B-NVFP4** 使用 NVIDIA 专有的 NVFP4 量化格式，该格式通过 FP4 权重与 FP8 Scale 的组合实现高压缩率和高计算效率。CUDA 13.0 能够直接调用 Blackwell GPU 原生支持的 FP4 Tensor Core 指令集，使模型推理过程能够以更低的显存占用、更高的计算吞吐完成大规模推理任务，从而充分释放 DGX Spark 的硬件潜力。

在多 GPU 通信与推理服务方面，CUDA 13.0 与 NCCL（NVIDIA Collective Communications Library）深度集成，可为 Tensor Parallel、Pipeline Parallel 以及分布式推理场景提供高效的数据交换能力。虽然本项目当前主要运行于单节点环境，但未来扩展至多 GPU 或 GPU 集群时，仍可基于 CUDA 与 NCCL 构建更大规模的模型服务能力，为系统扩展预留充分空间。

此外，CUDA 13.0 与当前主流 AI 软件生态保持高度兼容，包括 PyTorch、vLLM、TensorRT-LLM、FlashAttention、Transformer Engine 等关键组件均已完成适配。通过统一的软件栈，项目能够获得更加稳定的运行环境和持续的性能优化支持，降低不同组件之间的兼容性风险。

从工程实践角度来看，CUDA 13.0 不仅提供底层 GPU 计算能力，还承担了整个 AI 推理平台的运行时基础设施角色。项目中的文本生成、图像生成、音乐生成以及多 Agent 协同推理等任务，均通过 CUDA 调度 GPU 资源完成计算。借助 CUDA 提供的高性能并行计算能力，系统能够在有限的硬件资源下实现更高的模型吞吐量、更低的推理延迟以及更优的资源利用率。

综上所述，CUDA 13.0 作为 NVIDIA Blackwell 平台的重要软件基础设施，不仅为本项目提供了稳定、高效的 GPU 计算环境，也为 NVFP4 量化模型、vLLM 推理引擎以及多模态生成模型的高性能运行提供了关键支撑。通过 CUDA 13.0 与 DGX Spark 平台的协同优化，项目能够充分发挥新一代 GPU 架构优势，为复杂 AI 应用场景提供强大的算力保障。

#### 7.2.3 图像生成服务架构优化——基于 ComfyUI 的 Qwen-Image-Edit-2511 推理方案

在本项目的视觉内容生成模块中，我们采用 **ComfyUI** 作为图像生成与编辑工作流引擎，驱动 **Qwen-Image-Edit-2511** 图像编辑模型完成角色立绘生成、角色三视图生成、漫画页面渲染以及画面一致性优化等核心任务。

在第一代黑客松的 SparkScroll 项目中，图像生成服务主要基于 **vLLM-Omni** 及其官方 Docker 镜像进行部署，通过统一的大模型服务框架调用 Qwen 图像模型完成视觉内容生成。该方案具有部署简单、接口统一的优势，能够快速验证产品原型和生成链路。然而，在实际生产过程中，我们发现 vLLM-Omni 更偏向于多模态大模型的统一推理服务框架，其设计目标主要聚焦于模型服务化和接口标准化，而非针对扩散模型（Diffusion Models）或图像生成工作流进行专项优化。因此，在高分辨率漫画页生成、复杂角色一致性控制以及批量图像处理等场景下，GPU 资源利用率和推理效率存在进一步优化空间。

为解决这一问题，本项目引入了 ComfyUI 作为新一代图像生成执行框架。ComfyUI 采用基于节点（Node-Based）的可视化工作流架构，将模型加载、Prompt 处理、采样器调度、LoRA 加载、图像编辑、后处理等步骤拆解为独立节点，并通过计算图方式组织执行流程。相比传统的一体化推理调用模式，ComfyUI 能够更灵活地管理模型资源和计算过程，从而有效提升图像生成效率。

在实际部署过程中，我们针对 Qwen-Image-Edit-2511 构建了专用的图像生成工作流，将角色设定、参考图输入、风格控制、漫画页面生成以及图像增强等环节进行标准化封装。同时结合 ComfyUI 对模型缓存、显存管理以及推理流程的优化能力，显著降低了重复加载模型和重复计算所带来的性能损耗。

经过实际测试，在相同硬件环境下，第一代 SparkScroll 项目基于 vLLM-Omni 的图像生成方案，单张角色三视图或漫画页面的平均生成时间约为 **5~7 分钟**；升级至 ComfyUI 工作流后，单张图片生成时间稳定降低至 **1~2 分钟**，整体推理效率提升约 **3~5 倍**。这一优化显著缩短了从剧情生成到画面输出的等待时间，提高了整个多 Agent 创作流程的执行效率和用户交互体验。

除了性能提升之外，ComfyUI 还带来了更强的工作流编排能力。项目中的角色设计 Agent、分镜 Agent、漫画生成 Agent 以及后处理 Agent 均可以通过标准化工作流进行调用，实现图像生成过程的模块化管理。未来若接入新的扩散模型、ControlNet、LoRA、IP-Adapter 或视频生成模型，仅需调整工作流节点即可完成扩展，无需大规模修改业务逻辑代码，大幅提升系统的可维护性和可扩展性。

从架构层面来看，本次升级体现了项目从“模型调用驱动”向“工作流驱动”的演进思路。第一代 SparkScroll 更多关注模型能力验证，而本项目则更加重视内容生产链路的工程化效率。通过引入 ComfyUI，我们不仅获得了显著的性能提升，也建立起了适用于大规模视觉内容生产的标准化生成体系。

**综合来看，ComfyUI 与 Qwen-Image-Edit-2511 的结合，在保证图像质量和角色一致性的前提下，大幅提升了图像生成效率和系统扩展能力，为项目实现高效、稳定的视觉内容生产提供了重要支撑，同时也为后续接入更多多模态生成模型奠定了良好的技术基础。**
